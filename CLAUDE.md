## Architecture

- Everything runs in the browser; no backend (if one is ever added it must be Python).
- `src/db/worker.ts` runs PGlite in a dedicated Web Worker, boots empty (v12.0 P1: `initEngine`, `src/db/init.ts`: schema `sandbox` + `search_path = logistics, sandbox`; `initDb` = engine + Logistics, tests only), and executes one query at a time through `runSandboxed` (`src/db/run.ts`: `BEGIN` → query → `ROLLBACK`). PGlite rejects multi-statement input, so players cannot escape the rollback. Results over `MAX_ROWS_WORKER` (50,000) are cut and flagged `truncated`. The worker wraps `fetch` with `countingFetch` (`src/db/loadProgress.ts`) to report asset download bytes (`x MB`, or `x/y MB` when `Content-Length` is known). Every domain's tables come from worker request `ensure` (`ensureSchema`, `src/db/lab.ts`): Logistics is schema id `'game'` (chunk `gameSeed`, budget `gameseed`: creates schema `logistics` (`GAME_SCHEMA`, `src/domains.ts`, the only source of schema names) and sets `search_path` before `schema.sql` + `seed.sql`, so `public` stays empty), and only what the player opens is seeded (v12.0 P1). `DbClient`: `ENSURE_TIMEOUT_MS` 120 s; `ready(schema)` = engine up and that schema seeded; a request that names its schema seeds it first (queued ahead of itself); a failed seed is "broken" (requests no longer re-seed it) until `ensure()`/Retry. `main.ts`: `app.dbStatus` is the status of the open page's data (`want`), and `db.onSeeded` → `dataChanged()` (banner, caches, columns) runs after each seed; `openSchema` never replaces another banner, and a failed seed is retried only by Retry. `runLab` compares `pg_class.relname`, never `regclass` text.
- Seeded-DB snapshot (V16-OFFLINE, L143, spike S-a L137; `src/db/snapshot.ts`, worker only): the worker boots from IndexedDB `cargo-query-snap` / store `snap` / key `latest` (`{ format, pglite, schemas: { id: hash }, blob }`, gzip tar of the whole cluster: one record per browser) when `snapshotSchemas()` accepts it: `SNAPSHOT_FORMAT` (bump it when `ensureSchema`/`SANDBOX_SETUP_SQL` change what a seeded schema holds), the installed PGlite version and `__SEED_HASH__` (build-time hash of each schema's seed files, `scripts/offline.mjs`, `define` in `vite.config.ts`; a new seeded schema needs its files listed there) must match. `bootDb` unzips it itself (PGlite's own gunzip leaves an unhandled rejection on a corrupt blob), `loadDataDir`, checks the schemas exist, `DROP SCHEMA sandbox CASCADE` + `SANDBOX_SETUP_SQL` (UNLOGGED import tables come back empty; `DbClient` replays imports as after any restart), `markSeeded` (so `ensure` is a no-op). A mismatch deletes the record; a failed load boots empty and deletes it only once that empty boot works (offline without the engine's files is not the snapshot's fault); either way the schemas seed as before. After an `ensure` that seeded something new (`ensureTracked`) on a DB nothing else wrote to since the boot or the last seed (the next transaction id is unchanged: a rolled-back write leaves dead tuples that change plan costs, and moved sequences; read-only queries take no id), the worker queues `dumpSeeded` (`dumpDataDir('none')`, ~0.1 s, after the result is posted; none while `sandbox` holds a relation) and gzips + stores outside the queue (`mayReplace`: never over a record holding a schema the dump lacks, two tabs); it posts `snapshot` (client mark `db:snapshot`). `restart()` boots from the snapshot too. Not in dev (`import.meta.env.DEV`). Never `idb://` (L137). Snapshots carry `pg_statistic`, so plan costs equal the seed's (`tests/snapshot.test.ts`: md5, chapter 11 `Total Cost`, no dump after a rolled-back UPDATE, sandbox emptied, wrong key, corrupt blob).
- PWA (V16-OFFLINE, D-N6, L143): `public/manifest.webmanifest` (relative `start_url`/`scope`, works under any base) and a hand-written `public/sw.js`; the build prepends `VERSION`, `FILES` (every file in `dist/` except `datasets/`, V20-B) and `HTML_SHA256` (`writeServiceWorker`, `scripts/offline.mjs`, plugin in `vite.config.ts`). Install precaches the whole build (~26 MB, mostly PGlite) into cache `cq-<VERSION>` and fails unless `index.html` (fetched with `cache: 'reload'`) hashes to `HTML_SHA256`; navigations get the cached `index.html`, other same-origin GETs this version's cache (`ignoreVary`: module scripts send `Origin`, servers answer `Vary: Origin`), else the network; nothing is cached at runtime; `activate` drops other `cq-*` caches. No automatic `skipWaiting`, no `clients.claim`: `src/pwa.ts` (`initServiceWorker`, PROD only: the `controllerchange` listener at boot, `register()` 2 s after the first engine ready) shows `app.newVersion` with `apply` (posts `skipWaiting`) when a new version waits (also one already installing when it registers), and every controlled tab reloads on `controllerchange`, so no tab mixes versions.
- `src/db/client.ts` (`DbClient`) queues queries and posts one at a time, so the 5s timeout measures only the running query. `statement_timeout` does not work in PGlite, so a query over 5s terminates the worker and boots a fresh one. Errors are typed and carry no user-facing text (`SqlError` with `position`/`code`/`hint` for Postgres errors only, `WorkerTaskError` for non-Postgres worker failures such as an asset download or lazy chunk import, `QueryTimeoutError`, `DbRestartError`, `DbFailedError`); the UI translates them by class in `errorText()` (`src/ui/feedback.ts`). Do not switch to `PGliteWorker`: its multi-tab leader election breaks `terminate()`.
- `src/grader.ts` runs the player's SQL and the step's Solution on the same DB and compares by column position, as a row multiset (or sequence when `ordered: true`), with all numbers rounded to 2 decimals, unless the step has `precision: p` (frontmatter `precision:`, one number, or a list per step for a promotion review with `null` = none; L4): then a number not already at p decimals never matches (strict: `1235.00` and `1235` pass p = 0, `1234.6` does not). PGlite returns `numeric` as strings and `date` as `Date`. Chapter 11 also grades the plan (`src/planCheck.ts`, node types and planner cost from `EXPLAIN (FORMAT JSON)` without ANALYZE, never milliseconds): a step with `plan: { index: t }` must read table `t` through an index once the result is right; a step with `lab:` is an index lab, where the editor holds one `CREATE INDEX` and the worker (`runLab`, `src/db/run.ts`, request kind `lab`) explains the step's Solution before and after it inside one transaction that is always rolled back. The worker re-checks the statement (`isCreateIndex`: comments are stripped the way Postgres reads them, nested `/* */` and literals included; a backslash, a stray `*/`, `CONCURRENTLY` or a second statement is refused), runs it with `query()`, never `exec()`, and then requires `pg_class` to hold exactly one new relation, an index on the lab's table (else `LAB01`/`LAB02`, rolled back). A lab Run/Submit is recorded in the ticket's history (the DDL; ok = it ran) and clears `app.lastRun`, since it has no result table for the tabs to describe.
- Right but slow (v24 R0, L340–L344): `slowVerdict(solutionPlan, answerPlan, perf?)` in `src/planCheck.ts` compares the root cost and scans of two `EXPLAIN (FORMAT JSON)` plans (no ANALYZE). A drill or Postgres Engine lab step with `perf: { table, max_ratio? }` (and a `slow:` SQL its test proves is refused) is not passed when the answer loses the index on `table` or costs > 1.5 × the Solution (not a wrong submit; `perf.*`/`why.slow*` text); anywhere else a right answer > 3 × and > 1,000 is a weak pass with Boon's note (drills: `framed`). `work.ts` runs the two EXPLAINs after a right result (a failed EXPLAIN blocks only on `perf:`); Engine runners get it as `LabEnv.slow`. CI: `tests/perfGate.test.ts` (seeded schemas) and `tests/perfGateEngine.test.ts` (Engine setups) fail on cost > `GATE` budget or a non-sargable Seq Scan; exceptions only in their `ALLOW` tables, with reasons (stale entries fail).
