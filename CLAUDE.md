## Architecture

- Everything runs in the browser; no backend (if one is ever added it must be Python).
- `src/db/worker.ts` runs PGlite in a dedicated Web Worker, boots empty (v12.0 P1: `initEngine`, `src/db/init.ts`: schema `sandbox` + `search_path = logistics, sandbox`; `initDb` = engine + Logistics, tests only), and executes one query at a time through `runSandboxed` (`src/db/run.ts`: `BEGIN` → query → `ROLLBACK`). PGlite rejects multi-statement input, so players cannot escape the rollback. Results over `MAX_ROWS_WORKER` (50,000) are cut and flagged `truncated`. The worker wraps `fetch` with `countingFetch` (`src/db/loadProgress.ts`) to report asset download bytes (`x MB`, or `x/y MB` when `Content-Length` is known). Every domain's tables come from worker request `ensure` (`ensureSchema`, `src/db/lab.ts`): Logistics is schema id `'game'` (chunk `gameSeed`, budget `gameseed`: creates schema `logistics` (`GAME_SCHEMA`, `src/domains.ts`, the only source of schema names) and sets `search_path` before `schema.sql` + `seed.sql`, so `public` stays empty), and only what the player opens is seeded (v12.0 P1). `DbClient`: `ENSURE_TIMEOUT_MS` 120 s; `ready(schema)` = engine up and that schema seeded; a request that names its schema seeds it first (queued ahead of itself); a failed seed is "broken" (requests no longer re-seed it) until `ensure()`/Retry. `main.ts`: `app.dbStatus` is the status of the open page's data (`want`), and `db.onSeeded` → `dataChanged()` (banner, caches, columns) runs after each seed; `openSchema` never replaces another banner, and a failed seed is retried only by Retry. `runLab` compares `pg_class.relname`, never `regclass` text.
- `src/db/client.ts` (`DbClient`) queues queries and posts one at a time, so the 5s timeout measures only the running query. `statement_timeout` does not work in PGlite, so a query over 5s terminates the worker and boots a fresh one. Errors are typed and carry no user-facing text (`SqlError` with `position`/`code`/`hint` for Postgres errors only, `WorkerTaskError` for non-Postgres worker failures such as an asset download or lazy chunk import, `QueryTimeoutError`, `DbRestartError`, `DbFailedError`); the UI translates them by class in `errorText()` (`src/ui/feedback.ts`). Do not switch to `PGliteWorker`: its multi-tab leader election breaks `terminate()`.
- `src/grader.ts` runs the player's SQL and the step's Solution on the same DB and compares by column position, as a row multiset (or sequence when `ordered: true`), with all numbers rounded to 2 decimals, unless the step has `precision: p` (frontmatter `precision:`, one number, or a list per step for a promotion review with `null` = none; L4): then a number not already at p decimals never matches (strict: `1235.00` and `1235` pass p = 0, `1234.6` does not). PGlite returns `numeric` as strings and `date` as `Date`. Chapter 11 also grades the plan (`src/planCheck.ts`, node types and planner cost from `EXPLAIN (FORMAT JSON)` without ANALYZE, never milliseconds): a step with `plan: { index: t }` must read table `t` through an index once the result is right; a step with `lab:` is an index lab, where the editor holds one `CREATE INDEX` and the worker (`runLab`, `src/db/run.ts`, request kind `lab`) explains the step's Solution before and after it inside one transaction that is always rolled back. The worker re-checks the statement (`isCreateIndex`: comments are stripped the way Postgres reads them, nested `/* */` and literals included; a backslash, a stray `*/`, `CONCURRENTLY` or a second statement is refused), runs it with `query()`, never `exec()`, and then requires `pg_class` to hold exactly one new relation, an index on the lab's table (else `LAB01`/`LAB02`, rolled back). A lab Run/Submit is recorded in the ticket's history (the DDL; ok = it ran) and clears `app.lastRun`, since it has no result table for the tabs to describe.
- Tickets are markdown files in `content/tickets/chN/`, loaded by `src/content.ts` and parsed by `src/tickets.ts`. Ticket markdown is one lazy chunk (`src/ticketSources.ts`, budget group `tickets`; L41): `main.ts` awaits `loadContent()` (banner `content.loading`/`content.failed`) before the first render, but creates the `DbClient` before that await so the DB boots in parallel (its callbacks only record state until `uiReady`), and `tests/setup.ts` does the same for Vitest, so `loadTickets()`/`loadTicketTemplates()` stay synchronous but throw if called earlier. Never read tickets at module top level (`ui/modes.ts` builds its map on first use). VI text comes first, then a `# EN` block with the same sections (no SQL; SQL and frontmatter exist once). Frontmatter: `title_en`, `conclusion_en` (boss), `ordered`, `columns:` (one `{ vi, en }` business label per result column for the shape card, L25: never the Solution's column name; bosses have one list per step), `starter:`, `variants:`. Optional `## Task` holds the concrete request. Normal tickets have one `## Solution`; boss tickets have `## Step N: …` sections plus a `conclusion`. Use `textOf(ticket, lang)` for any player-facing ticket text. Copy `content/TEMPLATE.md` to start a ticket. Learning-method fields (Plan 2, curriculum §5): `format: worked | faded | open` (undefined = open); worked tickets add `## Example` after `## Task` (a ```sql block with `-- ①` markers in the VI part only, one prose paragraph per marker in VI and EN; `brief.ts` shows it with "Copy into the editor"); faded tickets have `___` blanks in `starter`; Submit (every exercise, and Thử ngay's check) refuses SQL while `blanksIn(sql, faded)` > 0 without counting a wrong submit (`src/tickets.ts`, v13 L94: faded counts every `___`, anything else only a standalone `___` outside strings and comments, so `LIKE '___'` passes; no Solution, `wrong:` or non-faded starter may hold one, `tests/blanks.test.ts`), and a run that fails with a blank left gets Boon's `sqlerr.blank` note instead of the SQLSTATE one; `reflect: { q, options, answer, why }` (bilingual, shown in the Recap, never saved); `wrong: [{ sql, vi, en }]` (`work.ts` shows the explanation when the player's wrong result equals one of them, else the trap of the skill the ticket teaches). Bosses use none of these. Prompts (body, Task, step text) are business questions with no table/column names, SQL keywords, status codes or backticks (`docs/team/problem-design.md` §1). `tests/content.test.ts` enforces backticks, uppercase SQL keywords, coded values and snake_case names; table names are plain English words, so those are review-only.

## Content and seed rules

- `src/db/seed.sql` is deterministic. Each random block starts with its own `setseed()`; append new blocks at the end only. PGlite is pinned to an exact version because `random()` output depends on the Postgres build.
- In-game "today" is 2026-10-31. Solutions use literal dates; `tests/content.test.ts` fails on `CURRENT_DATE`/`now()`.
- Ordered or top-N tickets set `ordered: true`, have an `ORDER BY`, and must state a complete tiebreaker in the prompt.
- Every table a Solution uses must be listed in the ticket's `tables` and unlocked by that chapter.

- Learning method (`tests/content.test.ts`, "phương pháp học"): every chapter has exactly one `faded` ticket (its first develop), every non-boss ticket has `reflect:`, and every `wrong:` SQL runs and differs from the Solution in every variant (Plan 6, L54); from chapter 4 the teach ticket is `format: worked` and every new skill has a non-boss ticket with ≥ 3 variants (L37). A rest ticket must `require` ≥ 2 skills of earlier chapters, one of them from chapter N−2 or older (`contentProblems`). Results never contain language-specific text: categories are numbers (1/2/3) and flags are booleans, because the grader compares strings exactly.

## Imported data (Plan Import)

- Player CSVs go to schema `sandbox` (`search_path = logistics, sandbox` (`GAME_SCHEMA`), set once in `initEngine`; game tables win on name clashes). Tables are `UNLOGGED`. The files never leave the browser: IndexedDB only, never uploaded, never copied into diagnostics (Plan 1c Task 11, if added).
- Flow: `inspectCsv` (`src/import/csv.ts`, main thread) checks every D3 limit (20 MB / 200k rows / 50 columns / 5 tables) and sanitises names to `[a-z0-9_]`: reserved words get `_`, game table names get `_my` (the static `LOGISTICS_TABLES` ∪ `ECOM_TABLES` ∪ `FIN_TABLES`, `src/domains.ts`, so no domain has to be seeded to check). Then `DbClient.importCsv` runs worker `kind: 'import'` through the query queue (30 s timeout, `COPY … FROM '/dev/blob'`, type inference in SQL). Then `idbStore().put` keeps the original file plus the inferred types (IndexedDB `cargo-query` / `imports`, records checked by `isStoredImport` on read).
- `DbClient` replays imported tables after every `restart()`. A replay that fails or times out is dropped and reported (`onImportDropped`), never retried in a loop. `MyData.restore()` replays IndexedDB on page load, one file at a time; a restart or failed boot keeps the stored file.
- Identifiers are inlined into SQL only through `ident()` and types only through `COLUMN_TYPES` (`src/db/import.ts`). Names reach Mermaid only through `mermaidName()`.
- Imported tables show only in Sandbox (`src/ui/myDataView.ts`): the "My data" section, the ER tab (`visibleTables()`), and autocomplete (via `schemaHooks.extra` in `src/state.ts`). Home has a "My data" mode card. When imported data changes, call `clearMemos()` (EXPLAIN / steps / ER caches are keyed by SQL text and schema name; `once()` is not cleared).
- Memory: the D3 limits stay (L5). The panel warns from `MEMORY_WARN_CELLS` imported cells (I3).
- IndexedDB code has no Node test beyond "no IndexedDB → no throw"; check it by hand (Plan Import Task 6 Step 9).
