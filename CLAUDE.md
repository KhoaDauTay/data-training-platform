# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Cargo Query: browser game for learning PostgreSQL as a data analyst at a fictional freight forwarder. Spec: `docs/superpowers/specs/2026-11-16-cargo-query-design.md`. Plans: `docs/superpowers/plans/`. Team decisions: `docs/team/amendments.md` (the user's decisions D1–D6 at the end override everything above them) and `docs/team/decision-log.md` (L1, L2, … override older plan/spec text).

## Commands

```bash
npm run dev                                   # Vite dev server
npm test                                      # all tests (Vitest, PGlite runs in Node; seed takes ~2s per DB)
npx vitest run tests/grader.test.ts           # one file
npx vitest run tests/grader.test.ts -t alias  # one test by name
npx tsc --noEmit                              # Vitest does not typecheck: run this after every change
npm run build                                 # typecheck + production build
```

## Architecture

- Everything runs in the browser; no backend (if one is ever added it must be Python).
- `src/db/worker.ts` runs PGlite in a dedicated Web Worker, seeds it via `initDb` (`src/db/init.ts`: `schema.sql` + `seed.sql`), and executes one query at a time through `runSandboxed` (`src/db/run.ts`: `BEGIN` → query → `ROLLBACK`). PGlite rejects multi-statement input, so players cannot escape the rollback. Results over `MAX_ROWS_WORKER` (50,000) are cut and flagged `truncated`. The worker wraps `fetch` with `countingFetch` (`src/db/loadProgress.ts`) to report asset download bytes (`x MB`, or `x/y MB` when `Content-Length` is known).
- `src/db/client.ts` (`DbClient`) queues queries and posts one at a time, so the 5s timeout measures only the running query. `statement_timeout` does not work in PGlite, so a query over 5s terminates the worker and boots a fresh one. Errors are typed and carry no user-facing text (`SqlError` with `position`/`code`/`hint`, `QueryTimeoutError`, `DbRestartError`, `DbFailedError`); the UI translates them by class in `errorText()` (`src/ui/feedback.ts`). Do not switch to `PGliteWorker`: its multi-tab leader election breaks `terminate()`.
- `src/grader.ts` runs the player's SQL and the step's Solution on the same DB and compares by column position, as a row multiset (or sequence when `ordered: true`), with all numbers rounded to 2 decimals. PGlite returns `numeric` as strings and `date` as `Date`.
- Tickets are markdown files in `content/tickets/chN/`, loaded by `src/content.ts` (`import.meta.glob`) and parsed by `src/tickets.ts`. VI text comes first, then a `# EN` block with the same sections (no SQL; SQL and frontmatter exist once). Frontmatter: `title_en`, `conclusion_en` (boss), `ordered`, `columns:` (one `{ vi, en }` business label per result column for the shape card, L25: never the Solution's column name; bosses have one list per step), `starter:`, `variants:`. Optional `## Task` holds the concrete request. Normal tickets have one `## Solution`; boss tickets have `## Step N: …` sections plus a `conclusion`. Use `textOf(ticket, lang)` for any player-facing ticket text. Copy `content/TEMPLATE.md` to start a ticket. Prompts (body, Task, step text) are business questions with no table/column names, SQL keywords, status codes or backticks (`docs/team/problem-design.md` §1). `tests/content.test.ts` enforces backticks, uppercase SQL keywords, coded values and snake_case names; table names are plain English words, so those are review-only.
- `content/skills.yml` (skill cards: label/syntax/when/trap) and `content/chapters.yml` (per chapter: `title`, `career` = the step reached by passing its promotion review, `tier` = ★ chapters 1/3/6/9/12 that change the job title, `story` shown on its first ticket, `outcomes`) are loaded by `src/progress.ts`, which also derives the title and career step from completed boss tickets (`rankOf()`), and holds linear progression, XP, which tables each chapter reveals (`CHAPTER_TABLES`) and `contentProblems` (soft-lock, pacing, skill-map and twist→boss checks).
- `src/save.ts` is the versioned progress save under localStorage key `cargo-query-save`. `graded` (same keys as `drafts`) holds the SQL that passed the grader, shown in the Recap; it is optional on disk (missing → `{}`, Recap falls back to the draft), so it needed no version bump. Bump `SAVE_VERSION` with a migration in `MIGRATIONS`; keep old fixtures in `tests/fixtures/` forever. Before migrating, the old save is copied to `cargo-query-save.v<old>`; an unreadable or newer save goes to `cargo-query-save.bak`. A failed write shows the `save.writeFailed` banner.
- UI: plain TypeScript DOM via `h()` (`src/ui/dom.ts`), no framework, styled with Tailwind CSS v4 (`@tailwindcss/vite`, L17). `src/state.ts` holds app state and selectors (no DOM); `actions` lets UI modules call back into `main.ts`. Two views, both always mounted and toggled with `hidden` (the editor is never recreated): Home `<main id="home">` (`ui/homeView.ts`) and the workspace `<main id="shell">`. Hash routes `#/` and `#/play` (`src/route.ts` pure, `ui/router.ts` DOM: `go()`, `currentRoute()`); Practice/Sandbox (Plan 1c) are modes inside `play`, not routes. One module per region: `ui/topbar.ts` (nav via `registerNav()`), `ui/inbox.ts`, `ui/brief.ts` (left pane: message, task, shape card, hints, conclusion, Recap; sender `avatar()` in `ui/avatar.ts`), `ui/work.ts` (editor, Run/Format/Submit, feedback, history), `ui/tabs.ts` (bottom panel). `ui/coach.ts` is the onboarding coach marks, `ui/splitter.ts` the resizable panes (`initLayout`), `ui/celebrate.ts` the small "pop" on a correct answer. `main.ts` only wires them together.
- Home is an ordered list of sections (`registerHomeSection({ id, order, span, render })`; it, `registerMode()` and `registerNav()` share `upsert()` from `src/registry.ts`: same id replaces): `harbor` 5, `continue` 10, `career` 20, `routes` 25, `chapters` 30, `kpi` 35, `skills` 40, `modes` 50. Built from the pure view-model `homeModel()` (`src/home.ts`: chapter status done/current/locked/soon, progress, skill level; `homeHooks.levelOf` takes Leitner boxes) and redrawn only while Home is visible. "Other modes" cards appear only when a feature calls `registerMode()`. The KPI dashboard (`content/kpis.yml`, `kpiTiles`/`kpiValue`) opens a tile only once its ticket is solved and computes the value from that ticket's Solution at runtime.
- Colleagues (L18): `content/people.yml` (`src/people.ts`) gives every sender a real role, bio, `tables:` (tables they own, real names from `schema.sql`) and `look` (`ui/avatar.ts` draws the SVG portrait). `roleLine()` is the line under a sender's name (role, then the unlocked tables they own). Department colours and thank-you keys live in one table, `DEPT` in `src/theme.ts`.
- Completion animations (L29, L31–L32, `docs/team/completion-animations.md`): `src/scene.ts` (pure, tested) has `sceneOf(ticket)` (boss → promotion, else `scene:` frontmatter, else by department/tables), `derive(tickets, completed)` (yard bays, open lanes, trips), `ROUTES` from Tien Sa and `STEPS` (every animation ≤ 3 s). `ui/harbor.ts` draws the Tien Sa scene and `ui/routeMap.ts` the route map with `s()` (`ui/svg.ts`, the `createElementNS` twin of `h()`); their SVG text hides below `lg` (it would render under ~11px), so Home repeats the key lines as HTML. `ui/stage.ts` `playCompletion()` runs from `complete()` only (first completion): it plays in the fixed `#stage` dock, announces through `#announce` (`aria-live`, both empty in `index.html`), is skippable (button or Esc, `stageEsc()`), never blocks input, and shows only the end state under reduced motion. Nothing new is saved.
- Styling: `src/style.css` keeps the colour tokens (`--bg`, `--panel`, `--accent`…, light + `prefers-color-scheme: dark`) and maps them to Tailwind with `@theme inline` (`bg-panel`, `text-muted`, `ring-line`, `bg-accent-soft`…), so neutrals need no `dark:`. `@layer base` restores button/heading/list/table/dialog defaults; `@layer components` keeps the shared class names `.muted .good .bad .warn .error pre.sql .stale .actions button.primary .tag` (later plans use them). Plain CSS remains only for the splitter layout (`--col`/`--row`), CodeMirror internals, the harbour's ambient `cq-*` keyframes and reduced motion. Tailwind scans only `index.html` and `src/**/*.ts`: every class must be a whole literal string (colour maps in `src/theme.ts`: `CHAPTER_COLOR`, `DEPT`; join with `cx()`); `tests/theme.test.ts` fails on template-literal classes. Text contrast ≥ 4.5:1 in both themes (white text only on -700 or darker).
- Editor (`src/ui/editor.ts`, CodeMirror 6): `Mod-Enter` runs (the selection if there is one, else everything), `Mod-Shift-Enter` submits, `Shift-Alt-F` formats; keymap at `Prec.highest`. `ui/work.ts` also listens on `document` (via `shortcutOf`, `src/ui/shortcuts.ts`) so Run/Submit shortcuts work when focus is outside the editor; the decision is the pure `pageShortcutOf()` (tested): it skips events the editor already handled (`defaultPrevented`), IME composition, dialogs and form fields, the hidden workspace (Home route), and Submit while the promotion-review conclusion form is open. Run/Submit close the autocomplete popup. Shortcut labels use `{mod}`/`{alt}`, which `t()` fills with ⌘/⌥ on macOS and Ctrl/Alt elsewhere. SQL errors are underlined via `setDiagnostics`. Syntax colours come from a small `HighlightStyle` using `--syn-*` CSS variables defined for both themes in `src/style.css` (no theme-one-dark). Other shortcuts and menus from spec §6b were dropped (decision L11).
- Render rule: `rerender()` redraws text (top bar, inbox, Home if visible, brief, `work.relabel()`, `relabelStage()`) and must never recreate the editor. `work.setTicket()` recreates it only when `ticketId#step` changes. Build or read that key only with `stepKey`/`ticketOfKey` (`src/save.ts`). Run/Submit capture ticket, step and editor at click time; a result that arrives after the editor was replaced only goes into that ticket's history (no lastRun, message or credit).
- Bottom-panel tabs register through `registerTab()` in `src/ui/tabs.ts` (group `output | query | schema`, then `order`) before `createPanel()`. Every tab describes `app.lastRun` (the last run, never the live editor) and shows a "SQL changed" strip when the editor differs.
- Visualizations (spec §6b) live in two layers: pure data builders in `src/viz/` (tested in Node against a real seeded PGlite; no translated text, only `import type` from `src/i18n`) and DOM/SVG renderers in `src/ui/*View.ts` (all text through `t()`, Tailwind classes, SVG via `s()`). `src/ui/vizTabs.ts` registers the five viz tabs (`chart`, `steps`, `explain`, `flow`, `erd`); load errors go through `errorView()`. EXPLAIN, execution steps and ER metadata are cached per SQL / schema with `memoByKey` (`src/viz/memo.ts`), so a language switch never re-runs them.
- Worker requests carry `kind: 'run' | 'explain' | 'steps'` and go through `DbClient.request()` (one queued request at a time; `steps` gets 3× the timeout).
- "Thứ tự thực thi" (`src/viz/steps.ts`) parses the player's SQL with `libpg-query` (Postgres' own parser, WASM), rebuilds one sub-query per logical clause with `pgsql-deparser`, and counts rows for each inside the sandbox. In the browser the `.wasm` must be imported via `?url` and passed to `loadModule` (`src/viz/parser.ts`); Vite does not bundle it otherwise. Failures are codes (`StepsFailure`), translated in the view. UI code imports step labels from the parser-free `src/viz/stepText.ts` (only types from `steps.ts`), so the parser stays out of the main chunk. WITH/UNION/window are not supported (curriculum §5.6).
- EXPLAIN uses `EXPLAIN (ANALYZE, FORMAT JSON)` inside `BEGIN … ROLLBACK` (`runExplain`); `src/viz/plan.ts` flattens it into nodes with typed `detail` and holds the VI/EN node glossary `NODE_HELP`.
- The ER tab renders a Mermaid `erDiagram` built from `information_schema` for a given schema (`loadErMetadata(run, schema)` in `src/viz/erd.ts`; `'public'` for the game, `'sandbox'` for imported data); it is the only place that uses `innerHTML` (Mermaid strict mode, schema identifiers only). Mermaid and the SQL parser are lazy-loaded.
- The workspace strip (`#map`, `src/ui/mapStrip.ts`, shown only on `#/play`) is one line (L35): the chapter's progress dots (`chapterDots`, `src/viz/progressDots.ts`), the open-lane count from `derive().open` and a link to Home. It draws no map: the Tien Sa route map lives on Home and in `playCompletion`. `main.ts` redraws it via `syncMap()` from `rerender()`.
- i18n: `src/i18n/vi.ts` is the key source; `src/i18n/en.ts` is `Record<Key, Msg>`, so a missing key fails `tsc`. All UI text goes through `t(key)`; static markup uses `data-i18n`/`data-i18n-aria`. EN plurals use function messages. Never translate table/column names, SQL, data values, Postgres error messages, or people's names and departments. `tests/i18n.test.ts` checks placeholders match and EN differs from VI (allow-list `SAME_OK`).
- Teaching errors: `src/ui/sqlErrors.ts` maps SQLSTATE (plus a few message regexes) to an explanation shown under Postgres' unchanged message; `tests/sqlErrors.test.ts` runs the wrong SQL on real PGlite.
- The shape card ("Expected result", `src/shape.ts`) shows column count/kinds, row count and the `columns:` labels, never the Solution's column names (they would give the answer away).
- localStorage keys besides the save, all device preferences wrapped in try/catch (`src/storage.ts`) and never part of `Save`: `cargo-query/prefs` (`{ lang }`), `cargo-query/layout` (splitter sizes), `cargo-query/coach-done` (onboarding skipped), `cargo-query/history` (last 15 queries per ticket id, shared by a boss's steps; Sandbox keeps none), `cargo-query/route` (last route, `home` | `play`). Every stored value is validated on read (`loadHistory`, `parseLayout`, `coachDone`): bad data is dropped, never thrown.
- Dependencies are pinned exactly: `@electric-sql/pglite` 0.5.16 (seed depends on it), `@codemirror/lint` 6.9.8, `@codemirror/language` 6.13.1, `@lezer/highlight` 1.2.5, `sql-formatter` 15.9.0 (lazy chunk, loaded by Format / Shift+Alt+F), `tailwindcss` 4.3.5 and `@tailwindcss/vite` 4.3.5 (dev). `libpg-query` 18.2.4 and `pgsql-deparser` 18.4.5 (lazy, loaded in the worker by the Execution order tab), `mermaid` 12.3.0 (lazy chunk, ER tab). Add new ones with `npm i --save-exact`.

## Content and seed rules

- `src/db/seed.sql` is deterministic. Each random block starts with its own `setseed()`; append new blocks at the end only. PGlite is pinned to an exact version because `random()` output depends on the Postgres build.
- In-game "today" is 2026-10-31. Solutions use literal dates; `tests/content.test.ts` fails on `CURRENT_DATE`/`now()`.
- Ordered or top-N tickets set `ordered: true`, have an `ORDER BY`, and must state a complete tiebreaker in the prompt.
- Every table a Solution uses must be listed in the ticket's `tables` and unlocked by that chapter.
- Each chapter must go teach → … → rest → boss, `requires`/`tables` must already be granted/unlocked, and every skill a twist ticket grants must be in the boss's `requires` (`contentProblems`).
- Every ticket ships VI + EN (release gate: 0 tickets without `# EN`). Code spans must be identical in VI and EN, EN must contain no Vietnamese diacritics, and `columns:` must have one label per Solution column (`tests/content.test.ts`).
- 12 chapters (L27, L30, `docs/team/curriculum.md`); chapter colours are `CHAPTER_COLOR` (1–12) in `src/theme.ts`, not YAML. A chapter with no tickets shows "Coming soon".
- Optional `scene: { kind, to?, lane? }` picks a ticket's completion animation (`ship yard customs truck quote ledger chat`; `to` is a port in `ROUTES`, only for `ship` or a boss; `lane` only for `customs`). The UI never says "boss" or "sự cố": a `beat: boss` ticket is a "promotion review" (L22; `tests/i18n.test.ts` scans i18n, content YAML and ticket text).
- New senders go into `content/people.yml` first (real role, `tables:`; `employee` = id in the seed's `employees`, or null).
- Story hooks the later chapters rely on are listed at the top of `seed.sql`; do not change them without updating tickets and `tests/seed.test.ts`.
- Project skills live in `.claude/skills/` (`web-games`, `level-design`, `save-systems`).
