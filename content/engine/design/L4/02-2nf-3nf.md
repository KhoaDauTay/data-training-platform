## Mở bài

Bảng `enrolments_flat` lặp tên khóa học ở mỗi lượt đăng ký, và `orders_flat` lặp thành phố của khách ở mỗi đơn. Cả hai đều đúng 1NF mà vẫn dính dị thường. Bài này tách chúng theo 2NF và 3NF, rồi chứng minh bằng SQL rằng không mất dòng nào.

## Ý chính

**2NF**: bảng ở 1NF và mọi cột không thuộc khóa phụ thuộc vào **cả** khóa, không vào một phần của nó. Chỉ bảng có khóa nhiều cột mới phạm được 2NF. Trong `enrolments_flat` khóa là `(student_id, course_id)`, nhưng `course_title` chỉ cần `course_id`: đó là **phụ thuộc bộ phận**, và tên khóa học bị lặp theo số học viên.

**3NF**: bảng ở 2NF và không cột không khóa nào phụ thuộc vào một cột không khóa khác. Trong `orders_flat`, `id` → `customer_id` và `customer_id` → `customer_city`: thành phố phụ thuộc vào khóa qua trung gian, gọi là **phụ thuộc bắc cầu**.

Cách chữa giống nhau: lấy vế trái của phụ thuộc có vấn đề làm khóa của một bảng mới, chuyển vế phải sang đó, giữ vế trái ở bảng cũ làm khóa ngoại. Phép tách như vậy là **không mất mát**: nối lại theo cột chung ra đúng bảng cũ, không thừa không thiếu. Nhiều người nghĩ cứ chia cột thành hai bảng là chuẩn hóa. Thật ra tách sai cột chung thì phép nối sinh ra dòng giả.

## Cú pháp

```sql
CREATE TABLE new_table AS SELECT DISTINCT determinant, dependent FROM wide_table;
ALTER TABLE new_table ADD PRIMARY KEY (determinant);
(SELECT ... FROM a EXCEPT SELECT ... FROM b) UNION ALL (SELECT ... FROM b EXCEPT SELECT ... FROM a);
```

- `CREATE TABLE … AS` chép cột và dữ liệu, không chép khóa, ràng buộc hay index.
- `DISTINCT` gộp các bản sao của cùng một sự thật thành một dòng.
- Hai chiều `EXCEPT` đều rỗng nghĩa là hai tập dòng bằng nhau.

## Ví dụ

Một bảng nhỏ phạm 2NF và bản tách của nó.

```sql
CREATE TABLE ex_enrol (student_id int, course_id int, course_title text, PRIMARY KEY (student_id, course_id));
INSERT INTO ex_enrol VALUES (1, 10, 'SQL'), (2, 10, 'SQL'), (3, 10, 'SQL'), (1, 20, 'Stats');
SELECT course_id, course_title, count(*) AS copies FROM ex_enrol GROUP BY course_id, course_title ORDER BY course_id;
```

Tên `SQL` nằm ba lần. Tách và thêm khóa:

```sql
CREATE TABLE ex_course AS SELECT DISTINCT course_id, course_title FROM ex_enrol;
ALTER TABLE ex_course ADD PRIMARY KEY (course_id);
SELECT course_id, course_title FROM ex_course ORDER BY course_id;
```

Giờ đổi tên khóa học chỉ sửa một dòng, và nối lại vẫn ra đủ bốn lượt đăng ký:

```sql
UPDATE ex_course SET course_title = 'SQL I' WHERE course_id = 10;
SELECT e.student_id, e.course_id, c.course_title FROM ex_enrol e JOIN ex_course c USING (course_id) ORDER BY e.student_id, e.course_id;
```

Hình cuối mục này vẽ phép tách đó: `course_title` chuyển sang `ex_course`, và nối lại ra đúng bốn dòng.

## Lỗi hay gặp

Tách theo một cột không phải khóa: hai khóa học trùng tên làm phép nối sinh dòng giả.

```sql
-- WRONG: split on the title, which is not a key; joining back invents rows
CREATE TABLE ex_twin (student_id int, course_id int, course_title text);
INSERT INTO ex_twin VALUES (1, 30, 'Intro'), (2, 31, 'Intro');
CREATE TABLE ex_st AS SELECT DISTINCT student_id, course_title FROM ex_twin;
CREATE TABLE ex_tc AS SELECT DISTINCT course_title, course_id FROM ex_twin;
SELECT count(*) AS rows_back FROM ex_st JOIN ex_tc USING (course_title);
```

```sql
-- FIX: split on the determinant course_id, which is a key of the new table
CREATE TABLE ex_sc AS SELECT DISTINCT student_id, course_id FROM ex_twin;
CREATE TABLE ex_ct AS SELECT DISTINCT course_id, course_title FROM ex_twin;
SELECT count(*) AS rows_back FROM ex_sc JOIN ex_ct USING (course_id);
```

Câu sai ra 4 dòng từ 2 dòng gốc: tên `Intro` khớp với cả khóa 30 lẫn 31, nên mỗi học viên nối với hai khóa học (2 × 2 = 4). Câu đúng ra đúng 2, vì `course_id` chỉ khớp một khóa học.

Sau khi tách và có khóa, database chặn luôn mâu thuẫn mà bảng rộng từng cho qua:

```sql
-- ERROR 23505: duplicate key value violates unique constraint "ex_course_pkey"
INSERT INTO ex_course VALUES (10, 'Another title');
```

Năm bước: tách `courses` khỏi `enrolments_flat`, thêm khóa, chứng minh không mất mát, rồi tách `customers` khỏi `orders_flat` và đọc kết quả.

## Tóm tắt

- 2NF: không cột nào phụ thuộc vào một phần của khóa nhiều cột.
- 3NF: không cột không khóa nào phụ thuộc vào cột không khóa khác.
- Tách theo vế trái của phụ thuộc: nó thành khóa của bảng mới và khóa ngoại ở bảng cũ.
- Kiểm không mất mát bằng `EXCEPT` hai chiều; `CREATE TABLE AS` không chép khóa, phải thêm lại.

# EN

## Opening

Table `enrolments_flat` repeats the course title on every enrolment, and `orders_flat` repeats the customer's city on every order. Both are in 1NF and still suffer anomalies. This lesson splits them by 2NF and 3NF, then proves with SQL that not one row is lost.

## Key idea

**2NF**: the table is in 1NF and every non-key column depends on the **whole** key, not on part of it. Only a table with a multi-column key can break 2NF. In `enrolments_flat` the key is `(student_id, course_id)`, but `course_title` needs only `course_id`: that is a **partial dependency**, and the course title is repeated once per student.

**3NF**: the table is in 2NF and no non-key column depends on another non-key column. In `orders_flat`, `id` → `customer_id` and `customer_id` → `customer_city`: the city depends on the key through a middle column, a **transitive dependency**.

The cure is the same: take the left side of the troublesome dependency as the key of a new table, move the right side there, and keep the left side in the old table as a foreign key. Such a split is **lossless**: joining back on the shared column gives exactly the old table, no more, no less. Many people think any split of columns into two tables is normalisation. In fact a split on the wrong shared column makes the join invent rows.

## Syntax

```sql
CREATE TABLE new_table AS SELECT DISTINCT determinant, dependent FROM wide_table;
ALTER TABLE new_table ADD PRIMARY KEY (determinant);
(SELECT ... FROM a EXCEPT SELECT ... FROM b) UNION ALL (SELECT ... FROM b EXCEPT SELECT ... FROM a);
```

- `CREATE TABLE … AS` copies columns and data, not keys, constraints or indexes.
- `DISTINCT` merges the copies of one fact into one row.
- Both `EXCEPT` directions empty means the two sets of rows are equal.

## Example

A small table that breaks 2NF, and its split.

```sql
CREATE TABLE ex_enrol (student_id int, course_id int, course_title text, PRIMARY KEY (student_id, course_id));
INSERT INTO ex_enrol VALUES (1, 10, 'SQL'), (2, 10, 'SQL'), (3, 10, 'SQL'), (1, 20, 'Stats');
SELECT course_id, course_title, count(*) AS copies FROM ex_enrol GROUP BY course_id, course_title ORDER BY course_id;
```

The title `SQL` is stored three times. Split it and add the key:

```sql
CREATE TABLE ex_course AS SELECT DISTINCT course_id, course_title FROM ex_enrol;
ALTER TABLE ex_course ADD PRIMARY KEY (course_id);
SELECT course_id, course_title FROM ex_course ORDER BY course_id;
```

Renaming a course now changes one row, and joining back still gives all four enrolments:

```sql
UPDATE ex_course SET course_title = 'SQL I' WHERE course_id = 10;
SELECT e.student_id, e.course_id, c.course_title FROM ex_enrol e JOIN ex_course c USING (course_id) ORDER BY e.student_id, e.course_id;
```

The figure at the end of this section draws that split: `course_title` moves to `ex_course`, and joining back gives exactly four rows.

## Common mistakes

Splitting on a column that is not a key: two courses with the same title make the join invent rows.

```sql
-- WRONG: split on the title, which is not a key; joining back invents rows
CREATE TABLE ex_twin (student_id int, course_id int, course_title text);
INSERT INTO ex_twin VALUES (1, 30, 'Intro'), (2, 31, 'Intro');
CREATE TABLE ex_st AS SELECT DISTINCT student_id, course_title FROM ex_twin;
CREATE TABLE ex_tc AS SELECT DISTINCT course_title, course_id FROM ex_twin;
SELECT count(*) AS rows_back FROM ex_st JOIN ex_tc USING (course_title);
```

```sql
-- FIX: split on the determinant course_id, which is a key of the new table
CREATE TABLE ex_sc AS SELECT DISTINCT student_id, course_id FROM ex_twin;
CREATE TABLE ex_ct AS SELECT DISTINCT course_id, course_title FROM ex_twin;
SELECT count(*) AS rows_back FROM ex_sc JOIN ex_ct USING (course_id);
```

The wrong query returns 4 rows from 2 original ones: the title `Intro` matches both course 30 and course 31, so each student joins two courses (2 × 2 = 4). The fixed one returns exactly 2, because `course_id` matches one course only.

Once split and keyed, the database blocks the contradiction the wide table used to let through:

```sql
-- ERROR 23505: duplicate key value violates unique constraint "ex_course_pkey"
INSERT INTO ex_course VALUES (10, 'Another title');
```

## Practice

Five steps: split `courses` out of `enrolments_flat`, add its key, prove the split is lossless, then split `customers` out of `orders_flat` and read the result.

## Recap

- 2NF: no column depends on part of a multi-column key.
- 3NF: no non-key column depends on another non-key column.
- Split on the left side of the dependency: it becomes the key of the new table and a foreign key in the old one.
- Check losslessness with `EXCEPT` both ways; `CREATE TABLE AS` copies no keys, so add them back.
