## Mở bài

Bảng `emp_skill_lang` ghi An biết `sql`, `python` và nói tiếng Việt, tiếng Anh, bằng cách lưu đủ bốn tổ hợp. Mỗi ngôn ngữ mới của An tốn hai dòng, mỗi kỹ năng mới tốn thêm số dòng bằng số ngôn ngữ. Bài này gọi tên chỗ lặp đó (4NF) và trường hợp hiếm hơn của nó (5NF).

## Ý chính

Phụ thuộc hàm nói "X quyết định một giá trị Y". **Phụ thuộc đa trị** X ↠ Y nói "X quyết định một **tập** Y, độc lập với các cột còn lại". Trong `emp_skill_lang`, `employee` ↠ `skill` và `employee` ↠ `language`: tập kỹ năng của An không đổi dù xét ngôn ngữ nào. Khi hai tập độc lập cùng nằm một bảng, bảng buộc phải giữ tích của chúng, và mọi thay đổi phải nhân lên.

**4NF**: bảng ở BCNF và mọi phụ thuộc đa trị không tầm thường đều có vế trái là siêu khóa. Cách chữa: tách mỗi tập độc lập ra một bảng, `emp_skills(employee, skill)` và `emp_languages(employee, language)`. Nối lại theo `employee` ra đúng tích cũ. Điều kiện quan trọng là "độc lập": nếu ngôn ngữ đi theo kỹ năng thì bộ ba là một sự thật và không được tách.

**Phụ thuộc nối** tổng quát hơn: bảng bằng phép nối của vài hình chiếu của nó. **5NF**: mọi phụ thuộc nối đều được suy ra từ khóa. Ví dụ kinh điển: đại lý bán sản phẩm của hãng, với luật "đại lý làm với hãng, hãng làm sản phẩm, đại lý bán sản phẩm đó thì đại lý bán sản phẩm đó của hãng". Bảng ba cột khi ấy tách được thành ba bảng cặp, nhưng không tách được thành hai. Thực tế 4NF và 5NF hiếm gặp: hầu hết thiết kế dừng ở 3NF hoặc BCNF là đủ, và lỗi thường gặp nhất ở đây là tách nhầm một bộ ba có nghĩa riêng.

Hình từng bước cuối mục này vẽ bốn dòng của An trong `emp_skill_lang`, rồi hai bảng sau khi tách.

## Ví dụ

Phụ thuộc đa trị hiện ra khi số dòng của mỗi nhân viên bằng tích số kỹ năng và số ngôn ngữ:

```sql
SELECT employee, count(*) AS rows_now, count(DISTINCT skill) * count(DISTINCT language) AS all_combinations
FROM emp_skill_lang GROUP BY employee ORDER BY employee;
```

Hai cột bằng nhau: bảng đang giữ đủ tích. Tách và nối lại bằng bảng phụ:

```sql
CREATE TABLE ex_skill AS SELECT DISTINCT employee, skill FROM emp_skill_lang;
CREATE TABLE ex_lang AS SELECT DISTINCT employee, language FROM emp_skill_lang;
SELECT (SELECT count(*) FROM ex_skill) + (SELECT count(*) FROM ex_lang) AS rows_after_split,
       (SELECT count(*) FROM emp_skill_lang) AS rows_before;
```

Tám dòng so với bảy: dữ liệu nhỏ thì chưa lợi về số dòng, nhưng giờ thêm một ngôn ngữ cho An chỉ tốn một dòng thay vì hai, và khi danh sách dài ra, khoảng cách là tích so với tổng. Phụ thuộc nối của 5NF, với bảng đại lý, hãng, sản phẩm:

```sql
CREATE TABLE ex_sales (agent text, company text, product text, PRIMARY KEY (agent, company, product));
INSERT INTO ex_sales VALUES ('Smith', 'Ford', 'car'), ('Smith', 'Ford', 'truck'), ('Smith', 'GM', 'truck'), ('Jones', 'Ford', 'truck');
CREATE TABLE ex_ac AS SELECT DISTINCT agent, company FROM ex_sales;
CREATE TABLE ex_cp AS SELECT DISTINCT company, product FROM ex_sales;
CREATE TABLE ex_ap AS SELECT DISTINCT agent, product FROM ex_sales;
SELECT ac.agent, ac.company, cp.product
FROM ex_ac ac JOIN ex_cp cp USING (company) JOIN ex_ap ap ON ap.agent = ac.agent AND ap.product = cp.product
ORDER BY 1, 2, 3;
```

Nối đủ ba hình chiếu ra đúng bốn dòng gốc.

## Lỗi hay gặp

Với bảng 5NF, chỉ nối hai hình chiếu là sinh dòng giả.

```sql
-- WRONG: two projections are not enough; Jones seems to sell Ford cars
SELECT count(*) AS rows_back FROM ex_ac JOIN ex_cp USING (company);
```

```sql
-- FIX: the join dependency needs all three projections
SELECT count(*) AS rows_back FROM ex_ac JOIN ex_cp USING (company) JOIN ex_ap ap ON ap.agent = ex_ac.agent AND ap.product = ex_cp.product;
```

Câu sai ra 5 dòng: Jones làm với Ford, Ford làm `car`, nên phép nối hai bảng tạo ra (Jones, Ford, `car`) dù Jones không bán `car`. Hình chiếu thứ ba (đại lý, sản phẩm) loại dòng đó, nên câu đúng ra 4.

Tách một bộ ba không độc lập: An chỉ dùng tiếng Việt cho `sql` và tiếng Anh cho `python`.

```sql
-- WRONG: language depends on the skill here, so splitting invents pairs
CREATE TABLE ex_tied (employee text, skill text, language text);
INSERT INTO ex_tied VALUES ('An', 'sql', 'vi'), ('An', 'python', 'en');
SELECT count(*) AS rows_back
FROM (SELECT DISTINCT employee, skill FROM ex_tied) s JOIN (SELECT DISTINCT employee, language FROM ex_tied) l USING (employee);
```

```sql
-- FIX: the triple is one fact; keep the table as it is
SELECT count(*) AS rows_back FROM ex_tied;
```

Câu sai ra 4 tổ hợp, trong đó 2 cái chưa từng đúng.

## Tóm tắt

- Phụ thuộc đa trị: X quyết định một tập Y độc lập với phần còn lại.
- 4NF: tách mỗi tập độc lập ra bảng riêng; bảng gốc là tích của chúng.
- 5NF: bảng chỉ tách đúng thành ba (hoặc hơn) hình chiếu; hai là chưa đủ.
- Chỉ tách khi các tập thật sự độc lập; bộ ba có nghĩa riêng thì giữ nguyên.

# EN

## Opening

Table `emp_skill_lang` records that An knows `sql` and `python` and speaks Vietnamese and English by storing all four combinations. Each new language of An's costs two rows, each new skill as many rows as there are languages. This lesson names that repetition (4NF) and its rarer cousin (5NF).

## Key idea

A functional dependency says "X determines one value of Y". A **multivalued dependency** X ↠ Y says "X determines a **set** of Y, independent of the other columns". In `emp_skill_lang`, `employee` ↠ `skill` and `employee` ↠ `language`: An's set of skills is the same whichever language you look at. When two independent sets share one table, the table must hold their product, and every change is multiplied.

**4NF**: the table is in BCNF and every non-trivial multivalued dependency has a superkey on its left side. The cure: give each independent set its own table, `emp_skills(employee, skill)` and `emp_languages(employee, language)`. Joining back on `employee` gives the old product exactly. The key condition is "independent": if the language goes with the skill, the triple is one fact and must not be split.

A **join dependency** is more general: the table equals the join of some of its projections. **5NF**: every join dependency follows from the keys. The classic example: agents sell companies' products, with the rule "if an agent works with a company, the company makes a product, and the agent sells that product, then the agent sells that product for that company". The three-column table then splits into three pair tables, but not into two. In practice 4NF and 5NF problems are rare: most designs are fine at 3NF or BCNF, and the most common mistake here is splitting a triple that has its own meaning.

## Example

A multivalued dependency shows when each employee's row count equals the number of skills times the number of languages:

```sql
SELECT employee, count(*) AS rows_now, count(DISTINCT skill) * count(DISTINCT language) AS all_combinations
FROM emp_skill_lang GROUP BY employee ORDER BY employee;
```

The two columns are equal: the table holds the whole product. Split it and join back with scratch tables:

```sql
CREATE TABLE ex_skill AS SELECT DISTINCT employee, skill FROM emp_skill_lang;
CREATE TABLE ex_lang AS SELECT DISTINCT employee, language FROM emp_skill_lang;
SELECT (SELECT count(*) FROM ex_skill) + (SELECT count(*) FROM ex_lang) AS rows_after_split,
       (SELECT count(*) FROM emp_skill_lang) AS rows_before;
```

Eight rows against seven: on small data the row count does not win yet, but adding a language for An now costs one row instead of two, and as the lists grow the gap is a product against a sum. The 5NF join dependency, with the agent, company, product table:

```sql
CREATE TABLE ex_sales (agent text, company text, product text, PRIMARY KEY (agent, company, product));
INSERT INTO ex_sales VALUES ('Smith', 'Ford', 'car'), ('Smith', 'Ford', 'truck'), ('Smith', 'GM', 'truck'), ('Jones', 'Ford', 'truck');
CREATE TABLE ex_ac AS SELECT DISTINCT agent, company FROM ex_sales;
CREATE TABLE ex_cp AS SELECT DISTINCT company, product FROM ex_sales;
CREATE TABLE ex_ap AS SELECT DISTINCT agent, product FROM ex_sales;
SELECT ac.agent, ac.company, cp.product
FROM ex_ac ac JOIN ex_cp cp USING (company) JOIN ex_ap ap ON ap.agent = ac.agent AND ap.product = cp.product
ORDER BY 1, 2, 3;
```

Joining all three projections gives exactly the four original rows.

## Common mistakes

For a 5NF table, joining only two projections invents rows.

```sql
-- WRONG: two projections are not enough; Jones seems to sell Ford cars
SELECT count(*) AS rows_back FROM ex_ac JOIN ex_cp USING (company);
```

```sql
-- FIX: the join dependency needs all three projections
SELECT count(*) AS rows_back FROM ex_ac JOIN ex_cp USING (company) JOIN ex_ap ap ON ap.agent = ex_ac.agent AND ap.product = ex_cp.product;
```

The wrong query returns 5 rows: Jones works with Ford and Ford makes `car`, so joining two tables creates (Jones, Ford, `car`) although Jones does not sell `car`. The third projection (agent, product) removes that row, so the fixed query returns 4.

Splitting a triple that is not independent: An uses Vietnamese only for `sql` and English only for `python`.

```sql
-- WRONG: language depends on the skill here, so splitting invents pairs
CREATE TABLE ex_tied (employee text, skill text, language text);
INSERT INTO ex_tied VALUES ('An', 'sql', 'vi'), ('An', 'python', 'en');
SELECT count(*) AS rows_back
FROM (SELECT DISTINCT employee, skill FROM ex_tied) s JOIN (SELECT DISTINCT employee, language FROM ex_tied) l USING (employee);
```

```sql
-- FIX: the triple is one fact; keep the table as it is
SELECT count(*) AS rows_back FROM ex_tied;
```

The wrong query returns 4 combinations, 2 of which were never true.

## Recap

- Multivalued dependency: X determines a set of Y independent of the rest.
- 4NF: give each independent set its own table; the original is their product.
- 5NF: the table splits correctly only into three (or more) projections; two are not enough.
- Split only when the sets really are independent; a triple with its own meaning stays whole.
