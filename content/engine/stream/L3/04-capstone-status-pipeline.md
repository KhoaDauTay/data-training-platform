## Mở bài

Cargo Query muốn đội chăm sóc khách hàng thấy trạng thái lô hàng gần như ngay khi nó đổi, mà không đọc thẳng database của đội giao vận. Bài tổng hợp này nối mọi phần của khóa học thành một đường đi, rồi kiểm tra consumer có đúng không khi topic có bản trùng và sự kiện sai thứ tự.

## Ý chính

**Đường đi.** Dịch vụ giao vận đổi `shipments` và ghi `outbox` trong cùng một transaction. CDC (ở đây là trigger, thay cho logical decoding mà PGlite không chạy) chép mỗi dòng outbox mới vào `change_log`. Relay đẩy `change_log` lên `topic` theo thứ tự `lsn`, khóa là mã lô, nên mọi sự kiện của một lô ở cùng partition.

**Topic không sạch.** Relay ít nhất một lần: sau một lần sập, thay đổi `lsn` 6 nằm trên topic hai lần. Và thứ tự trên topic chưa chắc là thứ tự phiên bản: `version` 3 của SHP-202 đến trước `version` 2, vì nó đi qua một đường gửi lại.

**Consumer đúng.** Upsert vào `current_status`, lấy phiên bản lớn nhất của lô và chỉ ghi đè khi mới hơn. Bản trùng không đổi gì (cùng phiên bản), sự kiện cũ đến trễ không kéo lùi được. Cuối cùng đối chiếu với `shipments`: dòng nào lệch thì giải thích được.

Hình cuối mục là cả đường đi, từ `shipments` tới `current_status`.

## Cú pháp

```sql
-- 1. change + outbox, one statement
WITH s AS (UPDATE shipments ...
  RETURNING shipment_id, status,
    version)
INSERT INTO outbox ... FROM s;
-- 2. relay, in lsn order
INSERT INTO topic (...)
SELECT lsn, after->>'aggregateid', ...
FROM change_log ORDER BY lsn;
-- 4. consumer: newest version wins
ON CONFLICT (shipment_id) DO UPDATE
SET status = EXCLUDED.status
WHERE c.version < EXCLUDED.version;
```

- `after->'payload'->>'status'`: `->` đi vào một trường jsonb, `->>` lấy giá trị ra dạng chữ.
- Năm bước dùng lại năm bài: outbox, CDC, bỏ trùng, phiên bản, đối chiếu.

## Ví dụ

Topic trước khi relay chạy: `lsn` 6 hai lần, `version` 3 của SHP-202 đến trước `version` 2.

```sql
SELECT seq, source_lsn, shipment_id,
  status, version
FROM topic
ORDER BY seq;
```

Trạng thái consumer đang giữ, cũ hơn nguồn:

```sql
SELECT c.shipment_id,
  c.version AS consumer_version,
  s.version AS source_version
FROM current_status c
JOIN shipments s USING (shipment_id)
ORDER BY c.shipment_id;
```

## Lỗi hay gặp

Sự kiện đến sau cùng thắng: SHP-202 lùi về `picked_up`.

```sql
-- WRONG: last arrival wins
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, seq DESC;
```

```sql
-- FIX: the largest version wins
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, version DESC;
```

Áp topic bằng `INSERT` thường: SHP-202 đã có trong `current_status`, nên cả câu bị từ chối.

```sql
-- ERROR 23505
INSERT INTO current_status
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, version DESC;
```

Đếm bản trùng theo lô hàng: SHP-202 có ba thay đổi khác nhau, không phải bản trùng.

```sql
-- WRONG: changes, not duplicates
SELECT shipment_id, count(*) AS copies
FROM topic
GROUP BY shipment_id
HAVING count(*) > 1;
```

```sql
-- FIX: one change = one source_lsn
SELECT source_lsn, count(*) AS copies
FROM topic
GROUP BY source_lsn
HAVING count(*) > 1;
```

## Thực hành

Năm bước theo đúng đường đi: ghi thay đổi và outbox, relay lên topic, tìm bản trùng, áp vào consumer, rồi đối chiếu với nguồn.

## Tóm tắt

- Thay đổi và outbox cùng một transaction; CDC và relay đưa nó lên topic theo thứ tự, khóa là mã lô.
- Topic có thể có bản trùng (relay gửi lại) và sự kiện sai thứ tự (đường gửi lại).
- Consumer đúng = upsert theo phiên bản: bản trùng vô hại, sự kiện cũ không kéo lùi.
- Đối chiếu với nguồn; lô chưa từng đổi chỉ có mặt nếu có snapshot ban đầu.

# EN

## Opening

Cargo Query wants customer service to see a shipment's status almost as soon as it changes, without reading the operations team's database directly. This capstone joins every part of the course into one path, then checks whether the consumer stays right when the topic has duplicates and out-of-order events.

## Key idea

**The path.** The operations service changes `shipments` and writes `outbox` in the same transaction. CDC (here a trigger, standing in for the logical decoding that PGlite cannot run) copies each new outbox row into `change_log`. The relay pushes `change_log` onto `topic` in `lsn` order, keyed by shipment id, so every event of one shipment sits in the same partition.

**The topic is not clean.** The relay is at least once: after a crash, change `lsn` 6 is on the topic twice. And the order on the topic is not necessarily the version order: SHP-202's `version` 3 arrived before `version` 2, because it came through a resend.

**A correct consumer.** Upsert into `current_status`, taking the shipment's largest version and only overwriting when it is newer. Duplicates change nothing (same version), and a late old event cannot move anything backwards. Finally reconcile with `shipments`: any row that differs can be explained.

The figure at the end of this section is the whole path, from `shipments` to `current_status`.

## Syntax

```sql
-- 1. change + outbox, one statement
WITH s AS (UPDATE shipments ...
  RETURNING shipment_id, status,
    version)
INSERT INTO outbox ... FROM s;
-- 2. relay, in lsn order
INSERT INTO topic (...)
SELECT lsn, after->>'aggregateid', ...
FROM change_log ORDER BY lsn;
-- 4. consumer: newest version wins
ON CONFLICT (shipment_id) DO UPDATE
SET status = EXCLUDED.status
WHERE c.version < EXCLUDED.version;
```

- `after->'payload'->>'status'`: `->` steps into a jsonb field, `->>` takes the value out as text.
- The five steps reuse five lessons: the outbox, CDC, deduplication, versions, reconciliation.

## Example

The topic before the relay runs: `lsn` 6 twice, SHP-202's `version` 3 before `version` 2.

```sql
SELECT seq, source_lsn, shipment_id,
  status, version
FROM topic
ORDER BY seq;
```

The state the consumer holds, older than the source:

```sql
SELECT c.shipment_id,
  c.version AS consumer_version,
  s.version AS source_version
FROM current_status c
JOIN shipments s USING (shipment_id)
ORDER BY c.shipment_id;
```

## Common mistakes

The last arrival wins: SHP-202 goes back to `picked_up`.

```sql
-- WRONG: last arrival wins
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, seq DESC;
```

```sql
-- FIX: the largest version wins
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, version DESC;
```

Applying the topic with a plain `INSERT`: SHP-202 is already in `current_status`, so the whole statement is refused.

```sql
-- ERROR 23505
INSERT INTO current_status
SELECT DISTINCT ON (shipment_id)
  shipment_id, status, version
FROM topic
ORDER BY shipment_id, version DESC;
```

Counting duplicates per shipment: SHP-202 has three different changes, not duplicates.

```sql
-- WRONG: changes, not duplicates
SELECT shipment_id, count(*) AS copies
FROM topic
GROUP BY shipment_id
HAVING count(*) > 1;
```

```sql
-- FIX: one change = one source_lsn
SELECT source_lsn, count(*) AS copies
FROM topic
GROUP BY source_lsn
HAVING count(*) > 1;
```

## Practice

Five steps along the path: write the change and the outbox, relay onto the topic, find the duplicates, apply to the consumer, then reconcile with the source.

## Recap

- The change and the outbox share a transaction; CDC and the relay bring it onto the topic in order, keyed by shipment id.
- The topic can hold duplicates (the relay resends) and out-of-order events (a resend path).
- A correct consumer = a versioned upsert: duplicates are harmless, old events cannot move it backwards.
- Reconcile with the source; a shipment that never changed only appears with an initial snapshot.
